# Release Notes v3.0.0

3.0.0 is a platform release. NGB has moved from Java 8 to **Java 21** and from Spring Boot 1.5 to
Spring Boot 3.5, and with them every third-party library the server is built on. The genome
browser itself is unchanged: no track type, panel or client feature was altered, added or removed,
and the target-identification feature described in the
[2.8.0 notes](../2.8.0/2.8.0.md) — a version that was never released — ships here for the first
time.

What *has* changed is nearly everything about running it. This page is written for whoever operates
an NGB instance.

## Before you upgrade

Two steps are **mandatory** for an existing instance, and neither can be done by NGB on its own.
Both are one-time.

1. **Convert the database.** H2 went from 1.3.176 to 2.3.232, which cannot open a 1.3 database
   file; the PostgreSQL driver and Flyway moved too. Follow
   [Upgrading the NGB database](../../installation/database-upgrade.md).
2. **Rebuild the search indexes.** Lucene went from 6.6.0 to 9.12.3, and Lucene 9 can neither read
   nor upgrade a Lucene 6 index. Follow
   [Rebuilding the Lucene indexes](../../installation/lucene-reindex.md).

Neither page applies to a fresh installation — an empty NGB creates its own database and builds its
own indexes.

Two more things to check, both of which have to be dealt with *before* you upgrade — after it,
neither is recoverable except from your backup:

* **Files registered from HDFS or GA4GH.** Those resource types are gone (see
  [Removed](#removed)), and a file still registered under one now fails as it is read — taking
  the whole request with it, so every dataset that contains such a file stops opening. The query
  that finds them, and what to do with them, is under
  [files registered from HDFS or GA4GH](../../installation/database-upgrade.md#before-you-convert-files-registered-from-hdfs-or-ga4gh).
  Most installations have none.
* **The gene-list spreadsheets you uploaded to targets**, if you are coming from a build of
  `develop` rather than from a release. Uploaded target gene lists live only in a search index —
  NGB does not keep the file — so that one index cannot be rebuilt from anything on disk. See
  [`targets/genes`](../../installation/lucene-reindex.md#targetsgenes-uploaded-gene-lists).
  Target identification ships for the first time in this release, so an instance upgraded from
  2.7.1 or earlier has no targets and nothing to check.

Take a copy of the database and of `files.base.directory.path` before you start. There is no
downgrade path: a converted database cannot be opened by NGB 2.x.

## Platform requirements

| | Before | Now |
|---|---|---|
| Java, server | 8 | **21** |
| Java, `ngb-cli` | 8 | **17 or newer** |
| PostgreSQL | 9.6 | 9.6 – 17 (tested on **16**) |
| Servlet container | embedded Tomcat 8, or a WAR in your own Tomcat | embedded Tomcat 10 only |

The server has to be started with one extra flag:

```
$ java -Xmx8G --enable-native-access=ALL-UNNAMED -jar catgenome.jar
```

Without `--enable-native-access=ALL-UNNAMED` every start prints three
`WARNING: A restricted method in java.lang.foreign.Linker has been called` lines. NGB works
either way; the warnings come from Lucene's memory-mapped directory reader, which uses the
foreign-memory API. The flag is already in the docker image, in the shipped launchers and in the
JRE-bundled archives — it only has to be added by hand if you run `java -jar` yourself.

## Removed

Features and integrations that are gone, with what to do instead:

| Removed | Notes |
|---|---|
| **HDFS / Hadoop file access** | `hdfs://` paths can no longer be registered. Files must be local, `http(s)://`, `s3://`, `sws://` or `az://`. A file *already* registered from HDFS has to be unregistered before you upgrade — see [Before you upgrade](#before-you-upgrade). |
| **GA4GH / Google Genomics** | The Google Genomics API this used was retired by Google. Registration of GA4GH datasets is gone from the API and from the CLI's resource types; the web client never offered it. Existing GA4GH registrations need the same treatment as HDFS ones, above. |
| **The Electron desktop application** | NGB is a server plus a browser client. The desktop build and its documentation page are gone. |
| **WAR packaging** | Only the executable jar and the docker image are built. NGB cannot be deployed into an external Tomcat any more. |
| **The index cache** | The in-memory tabix/BAM index cache is gone, and with it the `server.index.cache.enabled` property. Remove it from `catgenome.properties` — an unknown property is ignored, so leaving it in place is harmless but has no effect. Index reads on remote files are now per-request: a VCF's `.tbi` is re-fetched on every request, and a BAM's `.bai` is read in full three times per track load — 263 kB of transfer per request for an 88 kB index, measured against a local HTTP server. The cost scales with the size of the index, not with the window, so a human WGS `.bai` of 5–10 MB is paid on every pan. Local files are unaffected, and nothing is slower than the *first* request was before. |
| **SAML Holder-of-Key, IdP discovery and `/saml/web/**`** | `/saml/SSOHoK`, `/saml/discovery` and the extension's own configuration UI are gone: NGB talks to one identity provider, configured by properties. `LOGOUT_RESPONSE_SKEW` has nowhere to apply either — logout responses are not time-validated. The assertion skew and `saml.authn.max.authentication.age` are still honoured. |
| **OAuth2 login** (`spring-security-oauth2`) | JWT and SAML SSO are unaffected. Nothing in the client or the documentation ever offered OAuth2. |
| **The Google PaLM 2 LLM dependency** | `google-cloud-aiplatform` is gone from the build. The `GOOGLE_MED_PALM2` provider was already unusable — no handler implemented it and the server answered *"GOOGLE_MED_PALM2 is not supported"* — so nothing that worked has stopped working. The OpenAI GPT-3.5 / GPT-4 providers and the custom-endpoint provider are unchanged. |
| **The legacy `person` tables** | `PERSON`, `PERSON_ROLE` and `S_PERSON` are dropped by a schema migration on first start. No REST path changed: user and role management still answers on `/user`, `/users`, `/user/current` and `/role/**`, so the [administrator guide](../../user-guide/um-users.md) is accurate as written. |
| **Swagger 1.x API documentation** | Replaced by OpenAPI 3 — see below. |
| **nginx in the docker image** | The image installed nginx, never configured it and never started it. Put TLS termination, authentication and routing in a reverse-proxy container in front of NGB, as [docker/README.md](https://github.com/epam/NGB/blob/develop/docker/README.md) describes. |

## Changed

* **API documentation moved.** The spec is at `/catgenome/v3/api-docs` (OpenAPI 3.1) and the UI at
  `/catgenome/swagger-ui/index.html`. Swagger 1's `/catgenome/api-docs` is gone. Both paths are
  reachable without authentication under SAML, as `/api-docs` was.
* **The SAML login URL changed** from `/saml/login` to `/saml/login/ngb`. This is the endpoint NGB
  redirects an unauthenticated browser to; it appears in no metadata and in no identity-provider
  registration, so nothing has to be reconfigured on the IdP side — update it only if something of
  yours links to it directly. Every URL the IdP knows about, including the assertion consumer
  service and the SP metadata, is unchanged. The URL you land on after logging in now carries a
  `?continue` marker; that is Spring Security replaying the request you originally made, and is
  cosmetic.
* **Single logout is `POST /saml/logout`.** A `GET` on that URL used to end the identity provider's
  session as well as NGB's. It now clears the NGB session only and returns you to `/`, where the
  still-open IdP session silently signs you straight back in — which on a shared machine looks
  like logging out did nothing. The bundled web client submits the POST itself; a link or a script
  of yours that used `GET /saml/logout` has to be changed. `/saml/logout?local=true` is gone: a
  `GET` is now exactly that.
* **SAML behind a proxy or load balancer is configured with `saml.base.url`.** The `saml.lb.*`
  properties, and `saml.validate.url.without.scheme`, are gone — nothing derives the external URL
  from the incoming request any more — and an unrecognised property is ignored in silence, so a
  configuration left as it was looks like it is still working while publishing internal URLs in its
  metadata. Set `saml.base.url` (or `server.ssl.endpoint.id`) to the externally visible base URL.
  See [SAML SSO Authentication](../../installation/standalone.md#2-saml-sso-authentication).
* **The SP metadata now names the message-signing certificate.** NGB signed its SAML messages with
  `saml.sign.key` but published metadata built from the key store's default key — the HTTPS one —
  so an IdP configured *from* NGB's metadata was told the wrong key. Both are `saml.sign.key` now.
  An IdP configured by hand needs no change; one that reads the metadata will pick the corrected
  certificate up. The property names are unchanged.
* **The role hierarchy is in effect.** The old code built it with sixteen calls to a method that
  *replaces* rather than adds, so fifteen of them were discarded and the only relation that
  actually applied was `ROLE_SEG_MANAGER > ROLE_USER`. All fifteen intended relations now hold: in
  particular `ROLE_ADMIN` satisfies checks written against `ROLE_USER` and the manager roles, and
  because authorities are expanded through the hierarchy, an ACL entry granted to `ROLE_USER` also
  applies to administrators and managers. If you relied on an administrator *not* inheriting a
  permission granted to `ROLE_USER`, this changes what they can see.
* **On PostgreSQL, the predefined roles change on first start.** `ROLE_CYTOBANDS_MANAGER` and
  `ROLE_MAF_MANAGER` — neither of which any NGB release has ever used, and neither of which exists
  on H2 — are deleted along with their grants, and `ROLE_WIG_MANAGER`, which PostgreSQL never got
  and which nobody could therefore be granted, is created. Two surviving roles are renumbered.
  Roles you created yourself are untouched. Details, and what to do about a user who held
  `ROLE_MAF_MANAGER`, are in
  [Upgrading the NGB database](../../installation/database-upgrade.md#postgresql-only-schema-convergence).
* **An unauthenticated REST call gets 401, not a redirect.** With JWT security on, a request to
  `/restapi/**` without a usable token used to come back as a 302 to the SAML login page, because
  the error response was re-filtered onto the browser chain. API clients — including `ngb-cli`
  against a server that has both SAML and JWT enabled — now get the 401 they expect.
* **The documented docker volume paths were wrong, and are corrected.**
  [Docker installation](../../installation/docker.md) used to say to mount `/opt/catgenome/H2` and
  `/opt/catgenome/contents`. The image has worked out of `/opt/ngb` since 2.7.1, so those mounts
  were empty directories and the database stayed inside the container, to be lost with it. The
  paths to mount are `/opt/ngb/H2` and `/opt/ngb/contents`. Nothing about the image changed here —
  the documentation did; but if that is how your instance was set up, you have nothing persisted
  and nothing to convert.
* **The log4j configuration file is `log4j2.xml`**, not `log4j.xml`. The logging backend moved to
  log4j2 (slf4j 2 has no `slf4j-log4j12`). If you shipped a logging configuration of your own, it
  is now being ignored; rewrite it in log4j2's syntax under the new name.
* **`llm.custom.type=openai` now really talks to `llm.custom.url`.** Under the old Azure OpenAI SDK
  that combination silently went to `api.openai.com` — the endpoint was ignored — so a self-hosted
  OpenAI-compatible service configured this way was never actually being used. The current SDK
  honours the endpoint and sends Azure-shaped requests to it, which a non-Azure service will
  reject. For a self-hosted OpenAI-compatible endpoint use `llm.custom.type=custom`, which is
  NGB's own client; keep `openai` for a real Azure OpenAI resource. The `ChatGPT 3.5` and
  `ChatGPT 4.0` providers are unaffected.
* **The default BLAT search URL** is `https://genome.ucsc.edu/cgi-bin/hgBlat`. The old default,
  `http://genome.cse.ucsc.edu/cgi-bin/hgBlat`, no longer resolves to a usable endpoint. See
  [Known issues](#known-issues).
* **A custom `application.properties` may need editing.** Spring Boot renamed a number of its own
  properties between 1.5 and 3.x. Everything NGB itself ships is already correct, and NGB's own
  properties in `catgenome.properties` are unchanged apart from the removals listed above — but if
  you have overridden Spring or Tomcat settings of your own, check them against the
  [current list](https://docs.spring.io/spring-boot/docs/current/reference/html/common-application-properties.html).
  An unrecognised property is ignored silently.
* **AWS credentials are resolved by the AWS SDK v2 chain.** `AWS_ACCESS_KEY_ID`,
  `AWS_SECRET_ACCESS_KEY` and the `~/.aws/{credentials,config}` files documented in
  [Running NGB from standalone Jar](../../installation/standalone.md#configure-for-working-with-aws-s3)
  are read as before. One variable was renamed by the SDK: the profile file is now pointed at with
  `AWS_SHARED_CREDENTIALS_FILE` rather than `AWS_CREDENTIAL_PROFILES_FILE`. A region still has to be
  resolvable — from `AWS_REGION`, the config file or the instance metadata — or S3 access is
  disabled at startup with *"Unable to create S3 client, S3 services will be unavailable."*
  Note that `AWS_DEFAULT_REGION`, which earlier NGB documentation told you to set, is an AWS **CLI**
  variable that neither SDK version has ever read; if you set it, the region was coming from
  `~/.aws/config` or the instance metadata all along.

## Packaging and distribution

* **The JRE-bundled archives work.** `ngb-server-linux.tgz` and `ngb-server-windows.zip` carry an
  Eclipse Temurin 21 runtime, so they start on a machine with no Java installed: unpack, then
  `bin/ngb-server` (or `bin\ngb-server.bat`). Previous releases downloaded a JRE 8 from a URL
  Oracle removed in 2019, and the launchers they generated could not have found the bundled
  runtime even so. The launcher already passes `-Xms512m -Xmx2g --enable-native-access=ALL-UNNAMED`
  and *appends* `NGB_SERVER_OPTS`, so raising the heap is one setting and repeats nothing. The
  bundled runtime needs glibc 2.17 or newer (RHEL 7, Ubuntu 16.04 and later).
* **The docker image is built on `eclipse-temurin:21-jre-jammy`** instead of `ubuntu:16.04` plus
  `openjdk-8-jre`. `NGB_JAVA_OPTS` holds the JVM flags and `NGS_DATA_DIR` (default `/ngs`) the data
  root — the latter is read at container start now, where the old image baked the data root into
  the image at build time and `-e NGS_DATA_DIR=...` did nothing. `NGB_JAVA_OPTS` defaults to
  `-Xmx2G --enable-native-access=ALL-UNNAMED` and setting it **replaces** both flags, so keep the
  second one when you raise the heap or the startup warnings come back.
* **Builds run on GitHub Actions**, not AppVeyor, and now run the test suites. Artifacts are
  unchanged: `catgenome.jar` (H2), `catgenome-h2.jar`, `catgenome-psql.jar`, `ngb-cli.tar.gz` and
  `ngb-docs.tar.gz`.
* **Building from source needs more than a JDK**: the client is built with Node 14.17.5 and the
  documentation with mkdocs, both invoked by `./gradlew buildJar`. See the
  [README](https://github.com/epam/NGB/blob/develop/README.md).

## Known issues

* **BLAT search against UCSC's public endpoint does not work**, in this release or any earlier
  one. `hgBlat` now answers a programmatic query with a bot-protection challenge page instead of
  results, which NGB reads as zero hits. Point `blat.search.url` at a BLAT service that will answer
  programmatic requests to use the feature.
* **A plain, uncompressed feature file in cloud storage cannot be read.** VCF, BED, GFF/GTF, SEG
  and BEDGRAPH files addressed by `s3://`, `sws://` or `az://` must be bgzipped and tabix-indexed.
  This is not new in 3.0.0; it is documented under
  [Configure for working with AWS S3](../../installation/standalone.md#configure-for-working-with-aws-s3).
* **NGB's own properties cannot be overridden on the command line.** `ngs.data.root.path`,
  `file.browsing.allowed`, `blat.search.*`, `files.download.*` and about thirty more are read out of
  `catgenome.properties` itself rather than through Spring, so `--ngs.data.root.path=/data` — or the
  same key in `application.properties` — is ignored without a warning. Use `--conf=<directory>` and
  put the setting in the file. This is not new either; it is now written down, under
  [Configure data storage](../../installation/standalone.md#configure-data-storage).
* **PostgreSQL 17 has not been run.** The supported range quoted above is the JDBC driver's; NGB
  itself is built, tested and upgrade-rehearsed against PostgreSQL 16.
* **The JRE-bundled archives are not published.** They are built by CI on release branches and on
  manual runs, and attached to that run as artifacts; `build.sh` does not produce them and nothing
  uploads them next to the other release files. The Windows archive has also never been started on
  a Windows host — CI checks that it contains the JRE, the jar and the `.bat` launcher, and that it
  does not contain the broken POSIX one, which is what made the previous archives useless.
* **Azure, Swift and the LLM integrations were revalidated without a live service.** The Azure
  (`az://`), Swift (`sws://`) and LLM client libraries all moved several major versions in this
  release, and no Azure subscription, Swift endpoint or LLM API key was available while it was
  prepared: those paths are covered by unit tests and code review only. S3, `http(s)://` and local
  files were exercised against real and staged servers. Report anything that misbehaves.

## Why 3.0.0

The previous version number in the build files was 2.8.0, and it was never released — the last
released version is 2.7.1. 3.0.0 rather than 2.8.0 because this release removes functionality,
raises the Java and PostgreSQL floors, changes a login URL, and requires a database conversion and
an index rebuild that no operator can skip. The 2.8.0 release notes are kept as
[their own page](../2.8.0/2.8.0.md), marked as never released.
